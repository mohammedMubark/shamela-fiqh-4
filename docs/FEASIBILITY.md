# دراسة الجدوى — shamela-fiqh-4

## القرار الحالي

المسار العملي هو قراءة فهارس الشاملة الأصلية مباشرة، بنفس فكرة مشروع التفسير، بدل بناء فهرس مشتق.

الأسباب:

- الشاملة الحديثة تخزن نصوص الصفحات في Lucene لا في SQLite.
- SQLite لكل كتاب يعطي بنية مفيدة، لكنه لا يكفي للبحث النصي.
- فهرسة نسخة مشتقة تضاعف التخزين وتخلق خطر اختلاف بين النص الأصلي والفهرس.
- استخدام Lucene الموجود داخل `app/lucene/2` يحافظ على التوافق مع فهرس الشاملة دون شحن مكتبات Lucene.

## التصميم المختار

| القرار | النتيجة |
| --- | --- |
| محرك واحد `lucene` | لا ازدواج بين FTS5 وLucene |
| `helper/fiqh4-helper.jar` صغير | يشحن كود المشروع فقط |
| Lucene jars من الشاملة | لا تُشحن مكتبات Lucene |
| Java مكتشفة تلقائيًا | `FIQH4_JAVA_PATH` اختياري |
| SQLite read-only | metadata فقط: كتاب، مؤلف، جزء، صفحة، هيكل TOC |
| الاقتباس من `body` فقط | لا تُنسب الحواشي التحريرية للمؤلف |

## المخاطر الباقية

| الخطر | المعالجة |
| --- | --- |
| اختلاف تثبيت الشاملة | اكتشاف مسارات، وفحص `fiqh4_health` مفصل |
| تغير commit فهرس Lucene | بصمة المؤشر تتغير ويعود `CURSOR_STALE` |
| تصنيف مذهبي غير مؤكد | `unverified/needs_review` إلا عند override بشري |
| نصوص خبيثة داخل الكتب | `content_trust = untrusted_source_text` واختبارات prompt injection |
| نتائج ضخمة | دفعات، `total_hits` دقيق، تصدير تدفقي مع checkpoint |

## ما لا يضيف قيمة الآن

- Solr: يحتاج خادمًا ومنفذًا، وهذا خارج هدف الحزمة المحلية.
- Embeddings: تضر قابلية التدقيق والاستقصاء الكامل، وغالبًا تحتاج شبكة أو نماذج ضخمة.
- Python: وقت تشغيل ثانٍ بلا فائدة حاسمة هنا.
- فهرس SQLite مشتق: صار زائدًا بعد القراءة المباشرة من Lucene.

## شرط النجاح

الحزمة مقبولة عندما:

- تعمل من `.mcpb` مفكوك في مجلد مؤقت.
- تعرض الأدوات التسع في `tools/list`.
- ينجح `fiqh4_health` على `D:\shamela`.
- ينجح بحث فقهي حقيقي ويعود بنص قابل للإحالة.
- لا تتغير ملفات الشاملة.
- لا تشحن قواعد أو نصوص الشاملة أو Lucene jars أو JRE.
