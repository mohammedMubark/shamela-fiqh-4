## 2. المجموعة الكبيرة — 17 كتابًا / 77,000 صفحة

وُلِّدت بـ `node scripts/make-fixtures.mjs <dir> --scale 40`. الغرض منها اختبار الادعاءات
البنيوية — ثبات الذاكرة والاكتمال — على حجم لا يمكن أن يكون قد «رُتِّب» له.

| | |
| --- | --- |
| الصفحات | 77,000 |
| حجم بيانات المصدر | 25 م.ب |
| حجم الفهرس المشتق | **29 م.ب** |
| زمن بناء الفهرس | **3,181 م.ث** (~24,200 صفحة/ثانية) |

### زمن الاستجابة لدفعة واحدة

| النمط | المواضع المطابقة | p50 | p95 |
| --- | ---: | ---: | ---: |
| `phrase` | 3,215 | **17.71 م.ث** | 28.11 م.ث |
| `all_terms` | 1,943 | **21.38 م.ث** | 24.10 م.ث |
| `any_terms` | 70,035 | **115.45 م.ث** | 164.89 م.ث |

`discover_issue` على المجموعة كاملة: p50 **793.5 م.ث**.

### ثبات الذاكرة — القياس الحاسم

هذا هو الاختبار الذي يثبت أن حلقة الترحيل لا تُراكم النتائج. قيس بـ `--expose-gc` مع
`global.gc()` قبل كل قراءة لـ RSS:

| الاستعلام | المواضع | الدفعات | مكتمل؟ | **نمو RSS** |
| --- | ---: | ---: | :---: | ---: |
| `phrase` | 3,215 | 65 | ✅ 3,215/3,215 | **+27.9 م.ب** |
| `any_terms` | **70,035** | 1,401 | ✅ 70,035/70,035 | **+20.2 م.ب** |

**نتائج أكثر بـ 21.8 مرة، ونموّ ذاكرة أقل.** لا علاقة بين حجم النتيجة والذاكرة المستهلكة:
الحلقة تحمل دفعة واحدة، لا مجموعة النتائج.

### التصدير الشامل

| القياس | القيمة |
| --- | --- |
| المواضع المصدَّرة | **70,035** |
| الزمن | **7,605 م.ث** |
| المعدل | **9,209 موضعًا/ثانية** |
| نمو RSS | **+9.3 م.ب** |
| المكتوب على القرص | **66.2 م.ب** |

كتابة 66 ميغابايت مقابل نمو ذاكرة 9 ميغابايت — هذا هو الضمان التدفقي مقيسًا لا مُدَّعى.

### أثر تحسينَي الترحيل

قيس قبل التغيير وبعده على المجموعة الكبيرة نفسها:

| | قبل | بعد | الفرق |
| --- | ---: | ---: | ---: |
| ترحيل 70,035 موضعًا (مرتّب بالصلة) | 110.59 م.ث/دفعة | **90.91 م.ث/دفعة** | ‎−18% |
| تصدير 70,035 موضعًا | مرتّب بالصلة | **بترتيب المستند** | **7.6 ثانية** |

التحسينان:

1. **المؤشر يحمل الإجمالي الدقيق.** كان كل دفعة تعيد حساب `COUNT(*)` على مجموعة المطابقات
   كاملة. وهذا آمن لأن بصمة الفهرس مثبَّتة في المؤشر: مؤشر تغيّر فهرسه مرفوض أصلًا.
2. **المسح الشامل بترتيب المستند لا بالصلة.** الترتيب بالصلة يفرض اعتبار كل المطابقات لترتيبها؛
   والترتيب بالمستند يجعل شرط keyset ينتقل مباشرة إلى نقطة الاستئناف. والصلة بلا معنى حين
   تُؤخذ كل النتائج على أي حال.

### حدّ معروف، مذكور صراحةً

الترحيل العميق **المرتّب بالصلة** يظل مكلفًا: بلوغ الموضع 70,000 استغرق ~127 ثانية على 1,401 دفعة.
هذا قيد بنيوي في ترتيب bm25، لا خلل. **للاستقصاء الكامل استخدم `fiqh4_export_results`** —
نفس النتائج في 7.6 ثانية. الترتيب بالصلة مفيد للصفحات الأولى، وهو الاستعمال المقصود منه.

## 3. محرك Lucene الاختياري

| | |
| --- | --- |
| Lucene | 10.2.1 |
| حجم jar المبني | 7.8 م.ب (**لا يُشحن؛ يبنيه المستخدم**) |
| الصفحات المفهرسة | 1,925 |
| تطابق النتائج مع محرك Node | ✅ **متطابق تمامًا** |

اختبار `tests/integration/luceneParity.test.ts` يتحقق من أن المحركين يعيدان **مجموعة الصفحات
نفسها** في `phrase` و`all_terms` و`any_terms`، ونفس الإجماليات، ونفس العدّ لكل كتاب، ونفس أرقام
الصفحات المطابقة. الدرجات وترتيبها يختلفان (تطبيقا bm25 مختلفان) وهذا متوقع؛ أما مجموعة النتائج
فمتطابقة، وهو المطلوب.

**لم تُقس الفائدة الزمنية لـ Lucene قياسًا ذا دلالة** على هذه المجموعة الصغيرة؛ الفائدة المتوقعة
تظهر على مكتبة حقيقية بآلاف الكتب. وهذا رقم ينتظر قياسك.

## 4. أرقام مكتبتك الحقيقية — لم تُقس بعد

هذا القسم فارغ عمدًا. لن يُملأ برقم لم يُقس.

```bash
# على الجهاز الذي فيه المكتبة
npm run build

# ويندوز
set FIQH4_SHAMELA_DIR=D:\shamela
set FIQH4_INDEX_DIR=D:\fiqh4-index

npm run fiqh4:verify -- --out verify.json    # الفئات والتصنيف
npm run fiqh4:index                          # بناء الفهرس
npm run fiqh4:bench                          # الأداء
```

### ما يستحق الانتباه في نتائجك

- **زمن بناء الفهرس** ينمو خطيًا مع الصفحات. مكتبة بمليون صفحة تعني ~40 ثانية بالمعدل المقيس هنا.
- **حجم الفهرس** كان ~1.16 ضعف حجم بيانات المصدر في القياس أعلاه. خطّط لمساحة القرص على هذا الأساس.
- **`any_terms` بكلمات شائعة** هو أسوأ حالة: قد يطابق عشرات الآلاف من الصفحات.
  استعمل `phrase` أو `all_terms` للاستكشاف، وانتقل إلى التصدير للاستقصاء.
- إن كان **نمو الذاكرة يتناسب مع عدد النتائج** فذلك خلل يستحق الإبلاغ: المقصود ألا يتناسبا.
